# hills 0.12 — git-LFS datasets

Status: design, in progress on branch `feat/hills-0.12-lfs-datasets` (unreleased).

## Why

AutoLab is moving hill distribution from the custom `.hill.tar` bundle + lock
mechanism to plain **git repos + git-LFS** (bytes in object storage). hills 0.12
must evaluate a hill that arrives as an ordinary checked-out, LFS-smudged git
working tree, and must stop depending on the bundle/lock machinery for big files.

Constraint: **do not break scoring.** Identity stays the git tree hash; the report,
comparability, and ranking are unchanged. This is only about how the hill's files
get to the evaluator and how `materialize` lays them out.

## What changes

1. **Big files: git-LFS, not blob locks.** A hill marks large paths in
   `.gitattributes` (`filter=lfs`). Their pointers live in git (so they are in the
   tree hash, deterministically); their bytes live in LFS/object storage. The
   `blobs.lock` / `private.lock` mechanism and the `blobs.threshold`/`track` manifest
   fields are retired for new hills. `hills new` scaffolds a `.gitattributes` with
   sensible defaults (`*.parquet`, `*.zip`, `*.tar*`, `*.npy`, `*.bin`, `data/**`).

2. **`private/` is an ordinary directory.** No longer excluded from git and no
   `private.lock`. Large private files are LFS like any other. It stays a *soft*
   held-out convention (the agent is told not to read it); real gating is a separate
   future AutoLab feature. This means `private/` bytes are in the repo/LFS and are
   pulled by whoever can read the hill — an accepted, explicit trade for now.

3. **Git dir: accept `.git`.** A node obtains a hill with `git clone` (which makes
   `.git`), so `VC` must work with a normal `.git` repo. Keep reading `.vc` as a
   **legacy** layout (existing local hills) but prefer `.git` when present. New
   hills init a normal repo.

4. **`materialize` smudges LFS.** `git archive` emits LFS *pointer* files, not their
   content. So after archiving the committed tree into the run dir, replace every
   file that is an LFS pointer with a **symlink to the real, smudged file in the
   working tree** (`hill.root/<path>`), exactly as the old code symlinked blob-lock
   files — an evaluation still never copies gigabytes and never sees uncommitted
   content. Detect a pointer by its content signature
   (`version https://git-lfs.github.com/spec/v1`), so the library needs no git-lfs
   binary for a hill that has none.

5. **Bundles.** `hills bundle`/`unbundle` become legacy (kept so old flows and any
   `.vc` hill still work); new distribution is git clone + `git lfs pull`, driven by
   AutoLab, not the library.

## What does NOT change
`eval.py` contract, report envelope, `comparability_key`/`rank_key`, `hills check`
semantics for the evaluator, `HILLS_HOME`/`AUTOLAB_DATA` for evaluator caches, and
the `--current` (working tree, unofficial) and `--force` (last committed) eval modes.

## Materialize, precisely
```
materialize(dest):
  require a clean tree at the committed HEAD (the node guarantees this by
    detaching at the exact commit; a dirty tree is unofficial via --current)
  git archive HEAD -> dest                 # real for in-git files, POINTER for LFS
  for path in dest where file is an LFS pointer:
      replace dest/path with a symlink -> hill.root/path   # the smudged real file
  return dest
```
No lock verification (locks are gone); integrity is git's (the tree hash) plus
LFS's (oid = sha256, enforced by the LFS server on upload).

## Open questions for review
- Detecting LFS files: content-signature sniff (no git-lfs dep) vs `git lfs ls-files`
  (accurate but needs the binary). Lean: signature sniff, with `git check-attr` as a
  cross-check when available.
- Should `materialize` fail loudly if an LFS pointer's target is missing/not smudged
  (i.e. `git lfs pull` wasn't run) rather than symlinking a pointer? Yes — detect an
  unsmudged pointer in the working tree and error, so a mis-provisioned node can't
  score against pointer text.
- Back-compat: a `.vc` hill with existing `blobs.lock`/`private.lock` must still
  evaluate via the legacy path. Keep both paths, choose by which git dir + lock files
  exist.

## Codex review — adopted decisions (supersede the sketch above)

The direction (git tree + LFS objects, overlay materialization) stands, but the
implementation is revised for authoritative-scoring correctness:

1. **Raw tree export, not `git archive`.** `git archive` can alter bytes via
   `export-ignore`/`export-subst`/`info/attributes`. Materialize by enumerating
   `git ls-tree -rz` at the pinned commit and reading blobs via `git cat-file
   --batch`, recreating files/modes/symlinks exactly; reject gitlinks/submodules;
   intercept LFS pointer blobs during export.
2. **Strict pointer classification from the committed tree, not the working tree.**
   Use `git check-attr --source=<commit> filter` + a strict pointer parser of the
   raw committed blob. Consistency rules: `filter=lfs` + valid pointer → LFS;
   `filter=lfs` + empty blob → empty file; `filter=lfs` + other nonempty → hard-fail;
   pointer-looking blob without `filter=lfs` → hard-fail (ambiguous). **Reject `ext-*`
   extension pointers** (their oid may not equal the smudged bytes). No prefix-sniff;
   no dependency on the `git lfs` binary for classification.
3. **Verify every LFS object locally before eval.** For each LFS path: the smudged
   target is a regular file, size == pointer.size, sha256 == pointer.oid; else
   hard-fail with the path + expected oid + "run git lfs pull". Applies to official
   and `--current`.
4. **Stable materialized bytes, no live symlink into a mutable checkout.** Prefer a
   reflink/CoW copy of verified bytes into the run dir (fall back to a real copy);
   verify before eval and again before signing. A symlink is acceptable only under an
   explicit, enforced immutable read-only node contract.
5. **Pin one revision throughout.** Resolve `commit = rev-parse HEAD`,
   `tree = commit^{tree}` once, and drive export, attribute lookup, manifest load,
   tree hash, and report metadata from that exact commit — including the committed
   `hill.yaml` (a dirty manifest must never influence official params under `--force`).
6. **Select the materializer by manifest spec version, not by `.git`/`.vc` or
   `.gitattributes`.** Spec 1-3 → legacy lock materializer (both lock files required
   in the pinned commit). Spec 4 → LFS materializer (`blobs` field rejected, legacy
   locks rejected). A hill with real LFS pointers under spec 1-3 hard-fails
   (unsupported mixed storage).
7. **VC discovery.** Support a normal `.git` repo (`git -C <root>`); keep
   `--git-dir=.vc` for legacy. Hard-fail if both exist; verify the git top-level is
   exactly the hill root. `hills new` inits a normal repo; bundle-unpack inits legacy.
   NEVER run `write_exclude`/`refresh_exclude` on a normal repo (eval is read-only).
8. **`hills new`/commit must verify LFS is active** (filters + pre-push hook) and that
   every nonempty `filter=lfs` index blob is a canonical pointer before committing
   (else raw bytes get committed). Default `.gitattributes` includes `private/**` (not
   just `data/**`). Add a diagnostic for large non-LFS git blobs.
9. **Migration is a new tree identity** — a forward migration commit/new version, never
   `git lfs migrate import` over history. (AutoLab already scopes the leaderboard by
   `(hill, tree_hash)`, so pre/post-migration reports don't co-rank.)
10. **Bundles are strictly legacy.** `hills bundle` on a spec-4 hill fails clearly and
    points to git/LFS distribution; `hills unbundle` still builds a legacy `.vc` hill.
11. **Node runner:** clone into a dir named exactly the hill name (Hill.at requires
    it), detach at the exact commit, `git lfs pull`, then invoke hills (which
    re-verifies every LFS object).

## Decomposition (implementation order)
1. `hills/lfs.py` — strict pointer parse + classify + per-path verify (pure; unit-tested first).
2. Raw tree exporter (in VC).
3. VC `.git`/`.vc` discovery + pinned-revision resolution.
4. `LfsMaterializer` (spec 4) + keep `LegacyLockMaterializer` (spec 1-3); `_prepare_hill` returns one prepared object.
5. `hills new`/commit LFS-active checks + `.gitattributes` scaffold.
6. Bundle legacy-guards.
